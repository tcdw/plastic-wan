请为塑料碗实现「删除自己的闹钟」能力，并为跨 invocation 的工具查询结果增加一种可持久化的 internal context 机制。

## 背景

塑料碗是一个 Telegram 群聊 Agent。通常一条新的群友消息会触发一次新的 agent invocation，因此一次 invocation 中通过 tool 查询到的数据，不会天然存在于下一次 invocation 的上下文里。

现在已经有 alarm/定时提醒能力。我希望用户可以通过自然语言直接删除自己创建的闹钟，例如：

* 「把明天下午提醒我赶高铁的那个删掉」
* 「把第二个闹钟删掉」

用户不应该被迫经历「先让我列出所有闹钟 → 用户再确认 ID → 再删除」这样的 CRUD 式交互。Agent 应该可以自行查询、解析引用并在没有歧义时直接完成删除。

## 目标 1：新增 `list_alarm` 和 `delete_alarm`

新增两个 Agent tool：

### `list_alarm`

列出当前用户自己创建、目前仍然有效的 alarm。

主要用途有两个：

1. 用户主动询问自己有哪些闹钟；
2. Agent 为了完成自然语言形式的删除请求，在内部查询 alarm ID。

不要要求模型或用户提供 Telegram user ID。当前用户身份应该由 invocation/runtime context 提供。

返回的数据至少应足以让模型通过时间、summary 等信息识别具体 alarm，并包含后续 `delete_alarm` 所需的稳定 alarm ID。

默认不要返回已经触发、已经删除或其他不可再操作的历史 alarm。

### `delete_alarm`

根据 alarm ID 删除当前用户自己创建的 alarm。

权限校验必须在后端完成，而不是依赖模型判断。

即使模型获得或猜到了其他用户的 alarm ID，也不能删除。

如果 ID 不存在或不属于当前用户，不要向调用方泄漏该 alarm 是否真实存在；可以统一表现为类似 `not_found` 的结果。

如果用户已经通过自然语言唯一指向某个 alarm，应直接完成删除，不需要额外确认。

如果存在真正歧义，例如同时有多个 alarm 都符合「把提醒我出门的那个删掉」，再由 Agent 自己决定是否需要询问用户。

## 目标 2：跨 invocation 的 internal context

需要解决如下场景：

Invocation A：

用户：
「我有哪些闹钟？」

Agent 调用：

`list_alarm()`

得到：

* `alarm_abc`: 12:30，赶高铁
* `alarm_def`: 18:00，吃饭

Agent 向 Telegram 回复一个人类可读的列表。

随后 Invocation B：

用户：
「第二个删掉」

新的 invocation 必须能够知道上一轮展示给用户的「第二个」对应 `alarm_def`，从而直接调用：

`delete_alarm({ id: "alarm_def" })`

不要依赖模型重新从自然语言回复中猜测内部 ID。

### 设计要求

为 assistant 历史消息或相应的 assistant turn 增加一种 **internal context / internal note** 机制。

这个信息：

* 不发送给 Telegram 用户；
* 但在以后重新构建 Agent conversation history 时，可以作为隐藏的内部上下文重新暴露给模型；
* 必须持久化，不应只存在内存或 Redis；
* 应和现有会话历史使用相同的 durable storage（目前项目使用 SQLite）；
* 第一版主要用于保存 `list_alarm` 查询结果；
* 设计上不要把它限定死为 alarm 专用字段，因为未来可能用于其他跨 invocation reference resolution 场景。

例如未来可能需要支持：

* 「删掉你刚才查到的第二个」
* 「还是用刚才那个结果」
* 「把你刚才找到的那项改掉」

因此这更像 transient conversation working context，而不是长期 memory。

### internal context 的语义

internal context 应记录「当时这次 invocation / assistant turn 看到了什么」，而不是作为当前数据库状态的权威来源。

例如保存 alarm list 时，可以包含：

* alarm ID
* scheduled time
* summary
* 查询时间 / observed time（如果合适）

后续模型可以用它完成：

「第二个」 → `alarm_def`

这样的 reference resolution。

但是实际调用 `delete_alarm` 时，仍然必须重新经过数据库权限和状态校验，因为 alarm 可能已经触发、被删除或状态发生变化。

## 持久化设计

请先阅读现有：

* alarm schema / repository / service
* invocation persistence
* message persistence
* conversation history reconstruction
* tool execution/result handling

然后选择与当前架构最一致、最简单的设计。

可以考虑：

* 在 assistant message / invocation message 上增加 nullable JSON internal context；
* 或者建立独立的 internal-context 表；

但不要为了未来可能出现的需求过度设计。

目前优先级是：

1. 简单；
2. durable；
3. 能可靠 replay conversation；
4. 后续可以扩展更多 context 类型；
5. 不显著增加正常 history reconstruction 的复杂度。

不要为此引入 Redis。Redis 可以继续用于 ephemeral runtime state，但这种跟历史语义有关的信息需要在 SQLite 中持久化。

如果采用 JSON，请考虑版本化或明确的 type discriminator，避免未来变成无法维护的无类型 JSON 垃圾桶。

## Agent/tool 行为

tool description / prompt 中应表达清楚：

* `list_alarm` 可以作为内部辅助 tool 使用；
* 用户要求删除某个自然语言描述的 alarm 时，如果不知道 ID，可以调用 `list_alarm`；
* 如果查询结果可以唯一匹配，直接删除；
* 不要默认把完整查询结果展示给用户然后要求用户重新选择；
* 不要猜 alarm ID；
* 如果已有历史 internal context 足以确定 ID，可以直接调用 `delete_alarm`，无需重复 `list_alarm`；
* internal context 不等于当前真实状态，最终操作仍以数据库校验为准。

## 安全要求

请确保：

* 用户只能查询自己创建的 alarm；
* 用户只能删除自己创建的 alarm；
* ownership identity 来源于可信 runtime context，而不是模型参数；
* 不能通过 delete 结果探测其他用户 alarm ID 是否存在；
* internal context 永远不能直接发送给 Telegram 用户；
* internal context 中即使包含内部数据库 ID，也只应进入模型的隐藏上下文。

## 实现方式

请先调查当前代码结构，然后自行决定合理的 schema、类型和 abstraction。

尽量复用当前 alarm 和 invocation/message architecture，不要做与该功能无关的大规模重构。

完成后请：

1. 实现数据库 migration；
2. 实现 `list_alarm`；
3. 实现 `delete_alarm`；
4. 实现 internal context 的写入与 history reconstruction；
5. 在 `list_alarm` 被用于生成面向用户的 alarm 列表时，确保对应 ID mapping 可以被后续 invocation 使用；
6. 补充必要测试，尤其覆盖：

   * 用户只能看到自己的 alarm；
   * 用户不能删除别人的 alarm；
   * 自然语言列出 alarm 后，下一 invocation 可以用「第二个」对应到正确 ID；
   * alarm 状态在两次 invocation 之间变化时，删除能够安全失败；
   * internal context 不出现在 Telegram 实际发送内容中；
   * conversation reload/restart 后 internal context 仍然存在；
7. 跑相关测试、typecheck 和 lint；
8. 最后总结具体实现、schema 变化、关键设计决定，以及是否发现现有架构中需要注意的问题。
