# 塑料碗 Skills 机制设计计划

## 1. 背景与目标

塑料碗需要一套 Skills 机制，用于向模型提供：

- 特定任务的操作流程与说明；
- 按需加载的参考资料；
- 系统内置能力的使用方法；
- 后续由系统管理员安装的扩展能力。

塑料碗的运行环境具有一个重要前提：

> 模型会直接面对来自陌生群友等来源的不可信输入。

因此，Skills 不应被设计为模型可自行维护或修改的工作空间。无论是系统内置 Skill，还是未来由系统管理员安装的 Skill，对模型都应保持只读。

同时，希望在 Phase 1 就引入 Skills 的核心抽象，而不是等到容器化扩展能力完成后再重新设计一套 Skill 系统。

整体目标是：

1. Phase 1 即支持系统内置 Skills；
2. Skills 支持由多个 Markdown / reference 文件组成；
3. 系统 Skill 无需依赖 Bash 或任意代码执行能力；
4. 模型通过受控的 `execute` 调用宿主提供的能力；
5. Phase 2 增加管理员安装的 Skills，并允许其携带需要在隔离容器中运行的脚本；
6. 两阶段保持核心 Skill 组织形式与模型使用方式稳定；
7. 模型始终不能修改 Skill 本身。

---

# 2. 核心安全模型

Skills 分为两类：

### System Skills

由塑料碗发行版提供，是 runtime 的组成部分。

例如：

```text
system:///skills/yukino-wan/SKILL.md
system:///skills/yukino-wan/references/soul.md
system:///skills/yukino-wan/references/appearance.md
```

特点：

- 由塑料碗自身维护；
- 与 runtime 版本共同发布；
- 模型只读；
- 不提供任意脚本执行；
- 需要调用外部能力时通过 `execute`；
- 属于受 runtime 信任的系统资源。

### Admin Skills

Phase 2 引入。

由塑料碗实例的系统管理员安装，例如通过独立的 `/skills` 目录挂载进 Skill 执行容器。

特点：

- 不属于塑料碗发行版本身；
- 生命周期独立于 runtime；
- 对模型同样只读；
- 可以包含 references；
- 可以包含脚本；
- 脚本只能在隔离环境中执行；
- 安装、更新和删除由系统管理员负责，而不是 Agent。

这里刻意不提供类似 OpenClaw 中「Agent 修改自己的 Skill」的能力。

这是一个明确的安全边界：

```text
Untrusted user input
        │
        ▼
      Model
        │
   ┌────┴─────┐
   ▼          ▼
 read       execute
   │          │
   ▼          ▼
readonly    controlled
resources   capabilities
```

一次 prompt injection 不应具有修改 Agent 长期行为定义的能力。

---

# 3. Skill 文件结构

Skill 不是单个 `SKILL.md` 文件，而是一个只读资源包。

典型结构：

```text
yukino-wan/
├── SKILL.md
└── references/
    ├── soul.md
    ├── appearance.md
    ├── speaking-style.md
    ├── relationships.md
    └── boundaries.md
```

`SKILL.md` 主要负责：

- 描述 Skill 的用途；
- 描述何时应该使用；
- 指导模型按需读取 references；
- 描述可以调用哪些能力以及如何调用。

例如：

```md
当需要理解雪乃碗的核心人格时，读取：

references/soul.md

当需要描述她的外观时，读取：

references/appearance.md

当需要处理她与其他人物的关系时，读取：

references/relationships.md
```

这样可以避免大型 Skill 的所有资料被一次性加入 context。

模型只加载当前任务真正需要的部分。

---

# 4. `read`：统一的只读资源访问原语

Phase 1 增加 `read` tool。

其职责是读取模型有权限访问的虚拟资源。

例如：

```text
read("system:///skills/yukino-wan/SKILL.md")
```

以及：

```text
read("system:///skills/yukino-wan/references/soul.md")
```

`read` 本身：

- 无副作用；
- 不允许修改资源；
- 负责 URI resolution 和权限检查；
- 不承担 Agent reasoning；
- 不执行文件中的代码。

Skill 内部应尽可能允许相对路径引用。

例如正在读取：

```text
system:///skills/yukino-wan/SKILL.md
```

其中出现：

```text
./references/soul.md
```

或：

```text
references/soul.md
```

可以解析为：

```text
system:///skills/yukino-wan/references/soul.md
```

从而避免 Skill 内容硬编码自身完整安装路径。

---

# 5. `execute`：受控 Capability Gateway

Phase 1 不向模型提供 Bash 作为 Skills 的通用执行机制。

需要调用子能力时统一经过 `execute`。

`execute` 的定位是：

> 模型与宿主 capabilities 之间的受控 dispatch interface。

它不是另一个 Agent，不为模型提供执行任意脚本/代码的能力，也不负责替模型进行自然语言 reasoning。

模型负责：

- 判断需要什么能力；
- 查找适合的 tool；
- 阅读 tool help；
- 构造调用参数；
- 判断调用结果。

`execute` 负责：

- capability discovery；
- help/schema 查询；
- 参数 validation；
- 权限检查；
- dispatch；
- 返回结果；
- 调用审计。

概念上可以支持：

```text
execute
├── search
├── help
└── call
```

例如：

```ts
execute({
  action: "search",
  query: "公共交通路线规划"
})
```

得到候选能力：

```json
[
  {
    "name": "amap.transit_route",
    "summary": "规划公共交通路线"
  }
]
```

随后：

```ts
execute({
  action: "help",
  tool: "amap.transit_route"
})
```

最后：

```ts
execute({
  action: "call",
  tool: "amap.transit_route",
  input: {
    "...": "..."
  }
})
```

重要原则：

> `execute` 不接受一段自然语言任务然后自行完成 Agent routing。

否则它实际上会演变成隐藏的第二层 Agent runtime。

---

# 6. Phase 1：System Skills

Phase 1 即引入完整的 Skill 基础抽象，但只允许塑料碗自身提供 Skills。

资源结构大致为：

```text
system:///
├── AGENTS.md
├── docs/
│   └── ...
└── skills/
    ├── yukino-wan/
    │   ├── SKILL.md
    │   └── references/
    │       ├── soul.md
    │       └── appearance.md
    │
    └── another-skill/
        └── SKILL.md
```

### Phase 1 新增内容

#### Skill discovery

Runtime 能够向模型暴露当前可用的 System Skills。

Discovery 信息至少包含：

- Skill name；
- 简短 description；
- `SKILL.md` URI。

不需要把所有 Skill 的完整内容预先放进 context。

#### `read`

支持读取：

```text
system:///...
```

包括：

```text
system:///skills/...
```

#### `execute`

增加 capability discovery、help 和 call。

System Skills 所需的所有程序性能力原则上都通过 `execute` 提供。

#### Progressive disclosure

System prompt / Agent bootstrap context 只提供 Skill 索引。

模型判断某个 Skill 有关时，再：

```text
Skill index
    ↓
read SKILL.md
    ↓
read required references
    ↓
execute capabilities if needed
```

### Phase 1 明确不做

- 用户安装 Skill；
- 模型创建 Skill；
- 模型修改 Skill；
- Skill scripts；
- Bash；
- 任意代码执行；
- Skill container；
- 第三方 Skill 生命周期管理。

因此 Phase 1 可以在 Phase 2 的容器系统完成以前上线。

---

# 7. Phase 2：Admin Skills

Phase 2 不重新设计 Skills，而是在 Phase 1 的基础上增加第二种 Skill 来源。

此时：

```text
system:///skills/*
```

继续存在，并保持原有语义。

它仍然表示：

> 塑料碗 runtime 自带的系统 Skills。

与此同时增加管理员 Skills，例如：

```text
/skills/
├── foo/
│   ├── SKILL.md
│   ├── references/
│   └── scripts/
└── bar/
    └── SKILL.md
```

该目录独立挂载进入隔离容器，并保持只读。

模型侧可以通过独立资源域访问，例如概念上的：

```text
skill:///foo/SKILL.md
skill:///foo/references/example.md
```

具体 URI 名称可以在 Phase 2 实现时确定，但不与：

```text
system:///skills/...
```

混用。

因此即使出现：

```text
system:///skills/foo/
skill:///foo/
```

也不存在文件路径意义上的冲突。

---

# 8. System Skill 与 Admin Skill 的区别

两者共享相同的 Skill 文档组织协议，但并不是完全相同的安全主体。

| 能力             | System Skill    | Admin Skill               |
| -------------- | --------------- | ------------------------- |
| `SKILL.md`     | ✓               | ✓                         |
| references     | ✓               | ✓                         |
| 模型读取           | ✓               | ✓                         |
| 模型修改           | ✗               | ✗                         |
| 来源             | Runtime         | 系统管理员                     |
| 与 Runtime 一同发布 | ✓               | ✗                         |
| `execute`      | ✓               | 可支持                       |
| 携带脚本           | ✗               | ✓                         |
| 任意宿主代码执行       | ✗               | ✗                         |
| 脚本执行位置         | N/A             | 隔离容器                      |
| 信任等级           | Runtime trusted | Admin-installed extension |

关键区别不是：

> 一个只读，一个可写。

而是：

> 两者都只读，但拥有不同来源和不同执行模型。

---

# 9. Phase 2 的脚本执行模型

Admin Skill 可以包含：

```text
skill/
├── SKILL.md
├── references/
├── scripts/
└── includes/
```

整个 Skill tree 只读挂载进入容器。

这样脚本内部即使存在：

```python
from includes.foo import bar
```

或者 Node/Bun 中的相对 import，也可以正常访问完整 Skill 目录。

模型不能：

- 修改 script；
- 修改 include；
- 覆盖 `SKILL.md`；
- 写入 Skill tree。

需要产生临时文件时，应使用独立可写 workspace / tmp，而不是 Skill 目录。

因此：

```text
/skills      readonly
/workspace   controlled writable
/tmp         ephemeral writable
```

可以成为容器的基本 filesystem model。

---

# 10. `system://` 在 Phase 2 中的定位

Phase 2 不移除 `system://`。

相反，它的语义会更加明确：

```text
system:///
├── AGENTS.md
├── docs/
└── skills/
```

它只包含由塑料碗 runtime 自身提供的可信资源。

不会因为管理员 Skills 的加入而把 `system://` 变成通用 Skill filesystem。

这样：

```text
system:///skills/*
```

可以跟塑料碗版本一起升级。

而 Admin Skills：

```text
skill:///*
```

拥有独立安装和升级周期。

---

# 11. Skill 名称冲突

System Skills 与 Admin Skills 不共享同一个物理或逻辑 namespace，因此允许同名。

例如可以同时存在：

```text
system:///skills/web-search/
skill:///web-search/
```

不允许 Admin Skill 隐式覆盖 System Skill。

尤其不能采用类似 `$PATH` 的：

```text
user skill > system skill
```

shadowing 规则。

否则安装一个同名第三方 Skill 就可能改变系统原有行为，形成供应链攻击面。

Skill discovery 必须向模型明确暴露来源，例如：

```json
{
  "name": "web-search",
  "source": "system",
  "uri": "system:///skills/web-search/SKILL.md"
}
```

与：

```json
{
  "name": "web-search",
  "source": "admin",
  "uri": "skill:///web-search/SKILL.md"
}
```

如果需要引用具体 Skill，应使用完整身份，而不是依赖隐式覆盖规则。

# 12. 最终架构

Phase 2 完成后，整体可以抽象为：

```text
                       ┌─────────────────┐
                       │ Untrusted Input │
                       └────────┬────────┘
                                ▼
                           ┌─────────┐
                           │  Agent  │
                           └────┬────┘
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
              read           execute       script execution
                │               │                │
        ┌───────┴──────┐        │          isolated container
        ▼              ▼        ▼                │
   system://         skill://  capabilities      ▼
        │              │                  readonly /skills
        ▼              ▼                  writable workspace
 System resources   Admin Skills
 System Skills
```

其中最重要的边界是：

```text
Agent reasoning
      │
      ├── read trusted/installed readonly resources
      │
      ├── execute explicitly exposed capabilities
      │
      └── request execution of immutable admin-installed scripts
```

而不存在：

```text
Agent
  ↓
arbitrary bash on host
```

也不存在：

```text
Untrusted input
  ↓
Agent
  ↓
modify own skills
  ↓
persistent compromise
```

# 13. 实施顺序

## Phase 1

1. 定义 System Skill 目录与 manifest / `SKILL.md` 约定；
2. 实现 System Skill discovery；
3. 实现 `system://` URI resolution；
4. 实现 `read`；
5. 支持 Skill 内 references 和相对路径；
6. 实现 `execute.search`；
7. 实现 `execute.help`；
8. 实现 `execute.call`；
9. 将第一批内部能力迁移为 System Skills；
10. 用「雪乃碗人格」等大型多 Markdown Skill 验证 progressive disclosure。

Phase 1 完成后，Skills 已经是正式的 runtime abstraction，而不是 Phase 2 的临时 prototype。

## Phase 2

在保持 Phase 1 System Skills 不变的情况下增加：

1. Admin Skill discovery；
2. 独立 Admin Skill namespace / URI；
3. `/skills` 只读挂载；
4. Skill script execution；
5. 隔离 Docker runtime；
6. writable workspace / tmp；
7. Script dependency / relative import 支持；
8. Admin Skill 权限控制；
9. Admin Skill 与 runtime ABI / compatibility 声明；
10. Skill 安装、升级、删除生命周期管理；
11. System/Admin 同名 Skill 的明确来源展示与无 shadowing 解析规则。

---

# 14. 设计原则总结

整个 Skills 机制最终遵循以下原则：

**Skill 是只读能力包，而不是 Agent 自己维护的代码。**

**System Skill 属于 runtime；Admin Skill 属于管理员安装的扩展。**

**Markdown/reference 的读取与程序执行是两种不同能力。**

**`read`**** 负责知识和资源加载，****`execute`**** 负责受控 capability dispatch。**

**System Skill 默认不需要 Bash。**

**需要脚本的第三方/Admin Skill 在 Phase 2 使用隔离容器，而不是获得宿主 Bash。**

**模型负责 reasoning 和 tool routing；****`execute`**** 不成为隐藏的第二个 Agent。**

**Admin Skill 永远不能通过同名机制隐式覆盖 System Skill。**

**任何 Skill 都不能被来自不可信会话输入的 Agent 修改。**

通过这种方式，Phase 1 就可以开始实际使用并验证 Skills 协议；Phase 2 增加的主要是安装、隔离、脚本与权限能力，而不需要重新定义「Skill 是什么」。
