# Plastic Wan Runtime Configuration Hot Reload 调研与设计方案

> 状态：已确认方案边界，尚未实现。
> 日期：2026-09-18

## 1. 背景与动机

Plastic Wan 当前主要在进程启动时加载配置。修改配置后通常需要重启 `serve`，这会同时影响 Telegram polling、Scheduler、MCP、Sticker worker、Agent cache 和其他进程级组件。

热更新的目标不是把所有配置都变成可变状态，而是让适合 invocation 级生效的配置，在不重启进程的情况下影响后续工作。主要使用场景包括：

- 桌面客户端修改 Agent 配置后立即生效。
- 未来 Web / GUI configuration editor 保存后立即生效。
- Playground 临时调整 Prompt、模型和 Agent policy。
- 未来通过 HTTP / IPC configuration API 提交配置更新。
- 修改 Prompt、模型或运行策略时，避免为了简单配置变更而重启 Telegram polling 和整个 runtime。

该能力也为未来的多种更新来源提供统一应用入口：文件加载、桌面客户端、HTTP / IPC、测试代码和 Playground 都应能够复用同一个 parse / validate / apply 流程，而不是各自直接修改运行时组件。

热更新必须服从清晰的生命周期边界。它不意味着正在执行的 invocation 会突然切换 Prompt、model 或 tools，也不意味着 Provider、Telegram client、数据库路径、MCP topology 等所有进程级资源都必须支持替换。

因此，本设计的核心问题是：

> 哪些配置适合在 invocation 边界更新，哪些配置需要 component recreation，哪些配置仍应保持 process restart 边界？

## 2. 已确认的目标语义

Plastic Wan 未来支持 runtime configuration hot reload，但配置更新只影响更新之后开始执行的 invocation：

```text
配置版本 A
  → invocation queued
  → queued → running：取得 configuration snapshot A
  → 配置更新为 B
  → 已运行 invocation 继续使用 A
  → 后续 invocation 使用 B
```

本方案明确采用：

- **Configuration snapshot boundary**：`queued → running`。
- **Prompt 更新行为**：新 invocation 使用新 Prompt；现有 `systemPromptHash` 机制继续负责检测变化并重建 Conversation Context。
- **MVP 范围**：只支持 Agent / Prompt / invocation policy。
- **更新入口**：只提供显式 `reloadFromFile()`，暂不实现 filesystem watcher。
- **失败处理**：validate-before-swap；新配置失败时继续使用最后一个有效配置。

## 2. 当前配置生命周期

### 2.1 加载入口

配置当前在 `serve()` 启动时加载：

- `src/cli-options.ts`：解析显式 `--config`。
- `src/cli.ts`：加载 dotenv 文件并分发 CLI 命令。
- `src/application.ts:41-43`：调用 `loadConfig()` 和 `assertConfigPermissions()`。
- `src/platform/config.ts:287-318`：完成配置读取、解析、校验、Prompt 加载和 hash 计算。

当前 `serve` 启动后不会再次调用 `loadConfig()`。

### 2.2 parse / validation / normalization

`src/platform/config.ts` 的处理顺序：

1. `resolve(path)` 得到绝对配置路径。
2. UTF-8 读取配置文件。
3. 去除 BOM 后用 `jsonc-parser` 解析 JSONC，允许 trailing comma。
4. 使用 TypeBox 严格 Schema 校验，未知字段拒绝。
5. 执行语义校验：timezone、ID 唯一性、Provider/Model 引用、MCP policy、Context 参数关系等。
6. 读取 `agent.system_prompt_file` 和各 Chat 的 `instructions_file`。
7. 去 BOM、拒绝 NUL、剔除 HTML 注释、校验 Prompt template。
8. 将文件路径字段归一化为 Prompt 文本，生成 `RawConfig`。
9. 对原始 JSONC 和 Prompt 原始内容计算 SHA-256，生成 `LoadedConfig.hash`。

主要类型：

- `FileConfig`：文件形状，保留 Prompt 文件路径。
- `RawConfig`：运行时形状，包含已加载 Prompt 文本。
- `LoadedConfig`：`RawConfig`、`FileConfig`、配置路径和 hash。

当前没有统一的完整 `normalizeConfig()`；部分默认值散落在消费者中，例如 `admins ?? []`、`mcp.servers ?? []`、`sticker_trigger_enabled === true`、Admin static dir 和 memory warning days。

### 2.3 启动期装配

`src/application.ts` 使用启动时的 `loaded.config` 构造：

- `SecretStore` 和 Telegram Bot。
- `SqliteStore`、ServeLock。
- `createModelRegistry()`。
- `AgentModelSwitcher`。
- `TelegramIngestion`。
- `MediaService`、`StickerService`、`McpManager`。
- `SystemResources`。
- `ConversationRuntime`。
- `AgentRuntime`。
- `BucketScheduler`、`BotCommandService`、`AdminServer`。

这些对象大多直接持有或复制启动时的 `RawConfig`。

## 4. 当前已有的 snapshot 机制

当前架构已经有几个可复用的边界。

### 4.1 消息 snapshot

`src/store/invocation-snapshot.ts:36-90` 在 invocation 创建或 attach 时，把当前 Message Revision 写入 `invocation_messages.snapshot_json`。

后续 Telegram 编辑不会改变已经冻结的 invocation 输入。

### 4.2 模型在 invocation 开始时读取

`src/orchestration/agent-runtime.ts:210-213` 在 `runInvocation` 开始时调用 `modelSwitcher.model()`。

现有 `/model` 和 Admin Model API 已经满足：

- 已运行 invocation 不换模型。
- 后续 invocation 使用新模型。
- 重启后恢复配置文件默认模型。

### 4.3 Tool registry 在 invocation 开始时建立

`src/orchestration/agent-runtime.ts:266-290` 为每次 invocation 创建并校验工具注册表，包含 runtime tools、internal capabilities、MCP tools 和条件暴露的 `zzz`。

工具 registry 被写入 invocation 审计；运行中不能切换。

### 4.4 Stable Prompt 与 Context rebuild

`src/orchestration/agent-runtime.ts:214-226` 根据当前模型能力、Agent Prompt、Chat instructions 等生成 stable system prompt 和 hash。

如果 `systemPromptHash` 改变，当前实现会：

1. 重建 Conversation Context。
2. 驱逐 ConversationRuntime 中的 Agent cache。
3. 以新 stable prompt 开始后续运行。

该行为是 Prompt hot reload 的自然落点，不需要另造 Prompt migration 机制。

## 5. MVP 支持范围

### 5.1 支持热更新

第一版只考虑以下 Agent / Prompt / invocation policy：

- `agent.system_prompt_file` 及加载后的 Prompt。
- Chat `instructions_file` 及加载后的 instructions。
- Agent provider/model 的默认选择。
- `agent.thinking_level`。
- `agent.context_stop_ratio`。
- `agent.context.max_wall_clock_seconds`。
- `agent.context.idle_grace_seconds`。
- `agent.rate_limits`。
- `agent.history_messages`。
- `agent.send_max_text_length`。
- `agent.send_disallow_blank_lines`。
- `agent.send_nudge_enabled`。
- `agent.daily_budget.max_tokens`。
- `agent.max_concurrency`，作为后续 invocation 调度策略。

这些配置不会在运行中动态改变已开始 invocation 的行为，而是在 snapshot 创建时冻结。

### 5.2 需要重启的配置：保存但不立即生效

以下变更不属于 MVP 热更新范围：

- Telegram token、Bot identity、long polling client。
- `data_dir`、database path、backup path。
- Admin host、port、enabled、static listener lifecycle。
- Provider topology、API、base URL、headers、credentials、模型注册表。
- Vision provider/model、Vision semaphore、Vision prompt version。
- MCP server 新增/删除、transport、command、URL、credentials、policy。
- Sticker Set 同步与后台视觉索引。
- System Skills manifest、技能目录和资源 root。
- media cache 路径和其他必须重建基础资源的字段。
- Telegram Chat/topic allowlist、ignored users、participation、`process_bot_messages`、sticker trigger。

这些配置可以由未来 Admin Panel 表单编辑和保存，但保存后**不会立即改变当前运行中的服务**。后端应在校验后返回 `restart_required`，并说明具体变更字段；表单需要明确标注“重启后生效”或等价提示。

因此需要区分两个状态：

```text
active runtime configuration：当前进程正在使用的配置 A
saved/desired configuration：配置文件中已保存、下次启动将使用的配置 B
状态：B 已校验，但 pending restart
```

在服务重启前：

- 当前进程继续使用 active configuration A。
- Agent / Prompt / policy 的热更新仍可按正常规则发布。
- restart-only 配置 B 不得被部分应用。
- Admin Panel 应显示待重启状态和受影响字段。

这些字段不是不能实现，而是不属于本 MVP 的 in-process component recreation 范围；它们采用“保存、告知重启、重启后生效”的生命周期，而不是“拒绝保存”。

## 6. 推荐 ownership / lifecycle 模型

配置不应继续由多个组件分别持有一个可变的 `RawConfig`，也不应通过修改共享对象实现热更新。

建议增加轻量的 runtime configuration owner，例如：

```text
src/platform/runtime-config.ts
```

建议抽象：

```ts
RuntimeConfigurationStore
  current(): RuntimeConfiguration
  beginInvocation(): InvocationConfigSnapshot
  reloadFromFile(): Promise<ApplyResult>
```

`RuntimeConfigurationStore` 负责：

- 当前 active configuration。
- configuration generation。
- config hash。
- 已准备好的 invocation policy / Prompt / model 引用。
- validate-before-swap。
- last-valid configuration。
- active configuration 与已保存 desired configuration 的状态区分。
- restart-required 字段分类及 pending restart 状态。

不要引入完整 dependency injection framework。组合根 `src/application.ts` 仍然负责装配组件；新 store 只负责配置生命周期和 snapshot 发布。

## 7. Invocation snapshot 设计

建议新增 `InvocationConfigSnapshot`，在 scheduler 把 invocation 从 `queued` 原子转为 `running` 时取得。

snapshot 至少应包含：

```text
configuration generation
configuration hash
agent provider/model
thinking level
stable system prompt + prompt hash
context stop ratio
max wall-clock deadline
history limit
idle grace
rate limits
send policy
该 invocation 的 tool registry / component generation
```

实现上不要求把所有对象序列化进 SQLite；snapshot 可以是内存中的不可变对象引用。为便于审计，建议 invocation 记录至少增加或关联：

- configuration generation。
- 实际 provider/model。
- tool registry hash（已有字段，可继续复用）。

当前 `invocations` 只保存 `config_hash` 和 `prompt_version`；由于 `/model` 是内存 override，仅凭 `config_hash` 不能确定实际模型。

### 7.1 边界顺序

建议 scheduler 的执行顺序为：

```text
1. 选中 queued invocation。
2. 读取 RuntimeConfigurationStore 当前 generation。
3. 完成 queued → running 状态转换。
4. 把 snapshot 传给 AgentRuntime.run()。
5. 运行期间不再从全局 store 读取配置。
```

Node 单线程事件循环可以保证在没有 `await` 的连续代码中取得一致引用；若未来有异步 update source，应由 configuration manager 使用 in-process mutex 串行 apply。

### 7.2 Long-lived invocation

一个长生命周期 invocation 可以 attach 后续 Bucket。所有 attach Bucket 必须继续使用第一次进入 `running` 时取得的 snapshot：

```text
Invocation I + Snapshot A
  ├── Bucket 1 → A
  ├── 配置更新为 B
  ├── Bucket 2 attach → A
  └── Bucket 3 attach → A

I 结束后
  └── next invocation → B
```

不能在 `injectPending()` 或每个 turn 中重新生成 Prompt、tools 或 policy，否则同一 invocation 会混合新旧语义。

## 8. reloadFromFile 流程

初版只需要显式调用，不绑定 filesystem watcher：

```text
reloadFromFile(path)
  → loadConfig(path)
  → parse JSONC
  → TypeBox schema validation
  → semantic validation
  → classify changed fields
  → if restart-only fields changed:
       persist desired configuration
       keep active configuration unchanged
       return restart_required
  → otherwise:
       load and normalize Prompt
       resolve required secrets
       prepare MVP runtime configuration
       success: atomic swap
       failure: retain previous active configuration
```

`restart_required` 不是校验失败：候选配置可以合法并成功保存，只是不能在当前进程内立即应用。服务重启后，启动流程再次加载已保存配置并使其生效。

### 8.1 失败分类

静态 validation 错误：

- JSONC 语法错误。
- Schema / unknown field 错误。
- 类型、范围、唯一性错误。
- Prompt template 错误。
- Context 配置关系错误。
- 自定义 Provider / MCP 静态引用错误。

组件 prepare 错误：

- SecretRef 无法解析。
- Provider/model 不存在或 capability 不满足。
- Vision output 超出模型限制。
- Required MCP 无法初始化。
- 路径无法创建。
- tool registry 校验失败。

Invocation-time 错误：

- Provider timeout。
- Telegram API 错误。
- MCP call 失败。
- Vision 外部服务失败。
- 外部 rate limit。

前两类应使本次 apply 失败；第三类属于 invocation 运行错误，不应阻止已验证配置发布。

### 8.2 Atomic apply

采用 candidate-first：

```text
active A
  │
  ├── load/validate/prepare candidate B
  │
  ├── B 失败 → A 继续 active
  │
  └── B 成功 → 一次性 publish B
```

不要先覆盖旧配置再尝试初始化新组件。这样不需要复杂 rollback，也不会出现 Prompt 已换、model registry 仍旧、MCP 又是另一版的半更新状态。

失败需要记录清晰的 configuration update error，但必须通过 `SecretStore.redact` 处理错误文本，不能泄露 credential。

## 9. Prompt 与 Context 语义

Prompt 文件内容参与配置 hash；Prompt 内容变化后：

- 正在运行的 invocation 继续使用旧 stable prompt。
- 后续 invocation 取得新 stable prompt。
- 若 system prompt hash 改变，现有 Conversation Context 按当前实现重建。
- Context rebuild 会丢弃保留 transcript 和 capability refs，这是当前 Context 设计的既有语义。

MVP 不设计 Prompt migration、旧 transcript 跨 Prompt replay 或配置版本历史。

## 10. Filesystem watcher 边界

本轮不实现 watcher。

未来 watcher 只能作为 adapter：

```text
filesystem watcher
  → debounce
  → configurationManager.reloadFromFile()
```

watcher 不应负责：

- JSONC 解析。
- Prompt 校验。
- Provider 初始化。
- 直接修改 AgentRuntime / Scheduler / MCP。
- 自己处理 last-valid 状态。

未来 Electron、GUI、HTTP、IPC、测试代码都应调用同一个 reload/apply 核心入口。

## 11. 未来扩展点

### Electron / GUI / HTTP API

外部更新来源只负责提供配置候选值或文件路径，统一进入：

```text
load / parse / validate / classify / prepare
  → ConfigurationManager.apply
```

API 应返回：

- apply 成功或失败。
- active generation。
- active hash。
- desired/saved configuration hash。
- `restart_required` 状态。
- 需要重启后生效的字段路径。
- 脱敏后的错误信息。

Admin Panel 表单应在字段级或分组级标注：

```text
此配置修改后需要重启服务端才能生效
```

保存 restart-only 字段后，界面应同时显示：

```text
已保存，等待重启生效
```

不能把“保存成功”显示成“当前运行时已生效”。

本轮不设计配置历史、多用户协作、分布式同步或完整 rollback API。

### Playground

未来可以从 production runtime configuration 创建 invocation snapshot，再对 snapshot 应用临时 override：

```text
production config
  → invocation snapshot
  → fork snapshot
  → temporary overrides
  → Playground invocation
```

关键约束是 Playground 不得修改 global production configuration。

## 12. 建议实施阶段

### Phase 0：配置 ownership 重构

- 新增 `RuntimeConfigurationStore` 和 `InvocationConfigSnapshot` 类型。
- 将 invocation runtime policy 的读取集中到 snapshot。
- 保持现有 `loadConfig()` 行为不变。
- 暂不实现外部 reload source。

### Phase 1：Agent / Prompt / policy MVP

- 实现 `reloadFromFile()`。
- 支持 validate-before-swap。
- 支持 generation/hash。
- 对 restart-only 字段执行 diff 分类：合法保存，但返回 `restart_required`，不改变 active runtime configuration。
- 在 `queued → running` 取得 snapshot。
- 已运行 invocation 不受更新影响。
- 添加失败保留 last-valid 的测试。
- 添加 Prompt hash / Context rebuild 测试。
- 为 Admin Panel 表单提供字段级“重启后生效”元数据。

### Phase 2：审计与管理入口

- 持久化 invocation generation 和实际 provider/model。
- 增加 configuration update 审计事件。
- 如有需要，再提供 Admin/API 调用入口。

### Phase 3：可选组件生命周期更新

单独评估 Provider registry、Vision、MCP、Sticker、Telegram ingress 等，不与 MVP 混合实施。

## 13. 关键测试范围

至少覆盖：

1. 合法配置 reload 后 generation 增加。
2. 非法 JSONC / Schema / Prompt 配置不会替换 active config。
3. Secret / model prepare 失败不会替换 active config。
4. invocation 在 `queued → running` 时取得 A，之后 reload 到 B，仍使用 A。
5. 后续 invocation 使用 B。
6. long-lived invocation attach 的 Bucket 继续使用 A。
7. Prompt 变化导致下一次运行按 system prompt hash 重建 Context。
8. model、Prompt、tool registry 不在 invocation 中途变化。
9. running invocation 的 wall-clock deadline 不因新配置改变。
10. 失败错误经过脱敏，不输出 secret。
11. 配置更新不依赖 filesystem watcher，测试直接调用 `reloadFromFile()`。
12. invocation snapshot 与 queued/running 状态变化的边界保持一致。

此外，当前 invocation 创建链路需要保持数据库一致性：

- `invocations`
- `invocation_buckets`
- `invocation_messages`
- Bucket state
- configuration generation metadata

这些写入必须处于明确的事务边界内。

## 14. 风险与待确认项

### 已确认

- snapshot boundary：`queued → running`。
- Prompt 更新触发既有 Context rebuild。
- MVP 只更新 Agent / Prompt / policy。
- 初版只提供显式 `reloadFromFile()`，无 watcher。
- 失败保留最后有效配置。

### 后续仍需在实施前确认

1. `/model` 的 in-memory override 在 production config reload 后是否保留。
2. reload 中修改 `agent.provider/model` 时是否自动清理旧 override。
3. queued invocation 在配置更新后、尚未 running 时使用更新前还是更新后的配置；本方案按 snapshot boundary 定义为使用进入 running 时的 active config。
4. Prompt rebuild 后是否需要在 Admin Panel 明确显示 Context 已重建。
5. invocation 是否新增 `config_generation`、`model_provider`、`model_id` 字段，还是先只扩展审计 JSON。
6. restart-only 配置保存后，是否由 Admin Panel 提供“立即请求重启”操作；本方案当前只要求标记 pending restart，不要求服务自重启。
