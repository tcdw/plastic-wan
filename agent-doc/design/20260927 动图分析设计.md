# 动图分析：Storyboard、按时间补帧与观察缓存

设计记录：2026-09-27。目标是让聊天模型按需理解 GIF / Telegram animation 的内容、动作顺序和文字变化，同时限制解码、模型调用和重复分析成本。

## 1. 已认可方向与待定项

| 层级 | 内容 |
| --- | --- |
| 用户暂定 | 把关键帧拼成 storyboard，交给多模态 vision subagent；**每张 storyboard 最多 12 帧**。 |
| 初步认可 | 不够理解时，由 vision subagent 请求特定时间的画面，再继续分析；昂贵的分析应缓存。 |
| 初步认可 | 时间请求返回该时刻实际显示的完整合成画面及显示区间；缓存与聊天语境无关的观察，保留覆盖范围和不确定性。 |
| 本文建议 | 复用 `read_image`、`MediaService`、现有 Provider、并发门和审计；动图不进入静态图片直传；持久化结构化观察，单次分析内复用下载和帧。 |
| 尚未定值 | 总补帧量、轮数、墙钟时间、解码/输出预算、拼版分辨率、缓存 TTL 和最终时间归一化策略。 |

12 是单张 storyboard 的上限，不是单次分析总帧数，也不是准确率保证。[前期研究](../../docs/research/im-gif/README.md#对-llm-输入的建议有界起点不是已验证最优方案)中的“总计 24 张”只是实验建议，**没有被批准为产品预算**。

研究得到的 381 个有变化样本记录来自三个便利选取的公开仓库，不是 IM 流量分布；存在跨库重复。中文合集时长中位数约 1.5 秒，reaction 收藏约 2.82 秒，最长观测为 36.6 秒。它们支持“短片段优先、长尾另设预算”，不证明 12 帧足够。尚未进行 LLM 准确率评测或 Telegram 转码前后时序对照。

## 2. 输入范围与现有接入点

建议首期支持 Telegram `message.animation` 中的 GIF / 无声 H.264 MP4，以及作为 `document` 发送的 GIF。普通 `video`、任意 MP4 Document、APNG、动态 WebP、音频理解和动图发送不在首期范围；Sticker 搜索/索引的代表帧路径保持不变。

[Telegram GIF 说明](https://core.telegram.org/api/gifs)解释了上传 GIF 转为无声 MPEG-4 的行为；[Bot API Animation](https://core.telegram.org/bots/api#animation)定义同时覆盖 GIF 与无声 H.264/MPEG-4。不能仅在图片 MIME 白名单中添加 GIF。

## 3. 整体流程与入库分流

```text
Telegram animation / GIF document
  → allowlist、消息 Revision 与 media(kind=animation)
  → Context 只注入媒体标记 + img_ 引用（不自动附图）
  → 主模型通过 execute.call → read_image
  → 校验引用、TTL、媒体仍存在 → 当前分析版本缓存
  → 未命中：有界下载 / 解码 → 完整单轮时间轴 → 首张 storyboard
  → Vision 局部循环：请求时间帧 或 提交结构化观察
  → 校验观察与 runtime 覆盖记录 → 原子保存 → 返回不可信观察
```

入库建议：

- `message.animation` 优先于 `message.document`。[Message 契约](https://core.telegram.org/bots/api#message)明确 animation 会同时设置 document 以兼容旧客户端，必须只入一份媒体，不能重复计费或重复生成引用。
- GIF Document 与 Animation 都规范化为 `media.kind = animation`；仍保留原始 Telegram 元数据，标明来源，沿用消息修订和快照机制。
- MIME、文件名、声明时长/尺寸只是线索，不是安全判断。Animation 的可选 MIME/大小缺失不应自动归为静态图；下载必须有硬字节上限，并在转换前验证实际容器和编码。GIF Document 首期可要求 `image/gif`，不因文件后缀打开任意格式探测。
- 声明大小已超限时提前拒绝，缺失时仍由下载器限流；格式不符、MP4 含音频/非允许编码、时间轴不可确定时返回明确不支持/分析失败，不偷偷当一张缩略图成功。
- 保持静态图片现有分流：支持图片的主模型仍直接接收静态图。无论主模型是否支持图片，动图均走受限分析入口，避免两套不同的帧选择、缓存与计费语义。
- Context 继续由 `ConversationContextStore` 单写者维护；不把 vision 的局部逐轮 transcript 或 storyboard 二进制写入 canonical history，只保留外层工具调用、观察结果及必要引用。

## 4. 时间轴与取帧契约

### 4.1 完整显示状态

统一使用相对单轮首次显示的秒数，源时间基和精度保留在 metadata。单轮时长 `T` 不乘循环次数，循环信息单独记录。

- **GIF**：先按画布、局部矩形、透明度、背景与 disposal 合成完整画面，再建立显示区间；尤其覆盖 restore-to-background / restore-to-previous，不能把 delta 矩形当一帧图片。
- GIF 的缺失/零/极短 delay 必须使用明确、版本化的策略。研究采用缺失或 `<2 cs` 归一到 `100 ms`，但本机 FFmpeg 对 `1 cs` 保留 `10 ms`；这是实施前必须定案并用 fixture 固化的差异。不能一面按研究时轴标注、一面按默认解码时轴 seek。
- GIF user-input 等不能建成普通定时时轴的输入首期明确拒绝。循环只分析一轮；不能追逐无限循环。
- **MP4**：按解码后的 presentation timestamps 排序/定位，归零后建立显示区间；不能用 DTS、固定 FPS、关键帧位置或整数声明 duration 替代实际显示时间。末帧结束须来自可验证的时间信息，不可凭空补时长。
- 只合并**连续**像素完全相同的合成画面，保留合并后的 `[start, end)`。非相邻 A→B→A 必须保留两次 A；首期不增加感知去重或复杂场景检测。
- 顺序解码、有界缓冲；允许只保存时间索引、状态标识和所选画面。按需再次解码应复用本次下载，所有 pass 合计受解码预算约束，不把全部 RGBA 帧常驻内存。

研究发现容器 `format.duration` 可能不等于显示区间之和，尾部 XMP 扩展也可能被计为 packet。帧数来自真实解码图片，不能拿 packet 数代替。依据与复现见[研究的交叉验证记录](../../docs/research/im-gif/README.md#交叉验证发现的坑)。

### 4.2 按时间请求

`frameAt(t)` 的语义为返回满足 `start <= t < end` 的完整显示状态，而不是“最近的编码帧”或“最近关键帧”。

- `t` 必须有限且 `0 <= t < T`；负数、非有限数、越界和 `t = T` 明确报错，不静默夹取或取模。
- 初始采样直接选取已知末状态，不用请求 `T` 来凑末帧。
- 每项结果包含 runtime 生成的 `frame_id`、请求时间、实际显示起止时间、规范化尺寸及图片；同一状态命中多个时间点时复用帧并返回对应映射。
- 首轮 storyboard 中已出现的状态仍可按时间返回独立大图，以查看小字；不能因为时间相同就只返回“看过了”。复用像素文件不等于免除再次给模型看图的成本。
- `frame_id` 只是当前媒体/分析版本内的证据标识，不是可跨会话、跨媒体读取的 capability。补帧函数由外层已授权媒体闭包绑定，不接受 file ID、路径、URL 或另一份 `image_ref`。

## 5. 首轮采样与 Storyboard

建议以研究中的时间均匀策略为最小基线，先评测再调参。令 `S` 为连续去重后的状态段数：

1. `S = 1`：视觉上按单张静态内容处理，仍保留动图来源、时间轴和分析版本，不回落到未授权的直传路径。
2. `2 <= S <= 12`：每个状态一格。
3. `S > 12`：目标格数 `K = min(S, 12, max(4, ceil(2*T)))`；首尾占两格，内部目标 `i*T/(K-1)`，`i=1..K-2`。
4. 时间点映射到状态段后按时序去重，实际格数可以小于 `K`；不为凑满 12 格重复图片，也不跨时间去掉 A→B→A 中的 A。

Storyboard 按行从左到右、从上到下排序；布局随格数选择，不固定拉伸成 12 格。等比缩放、留边、不裁掉字幕，每格在图像内容外标注 `frame_id` 与真实起止时间；另附同样的文本 manifest、单轮总时长、循环信息和未采样区间。

每张最多 12 格不代表“拼成一张图就不花视觉 Token”。整图尺寸、单格可读分辨率、编码字节和每轮图片总量都要限额；不能套用静态图缩放后让文字小到不可读却报告看清。需要细节时用独立补帧图。首期不把多张 12 格拼版当绕过总帧预算的方法。

覆盖整条时间轴的**采样范围**不等于覆盖所有状态。对快闪文字、短动作与反转保持不确定性；若解码资源不够建成完整时轴，应失败或明确标记截断，不能截前几秒后伪称完整单轮。

## 6. 受限 Vision 循环与结果协议

这里的 vision subagent 指 `MediaService` 内的一段有界模型循环，不新增通用 agent 平台。沿用已配置的 vision 模型和[分析开始时的配置快照](../../src/capabilities/media/media.ts#L92)，整个循环固定模型、prompt、schema 和策略版本。

建议主模型继续调用 `read_image({ image_ref })`；为后续新问题补看，可增加可选、限长的 `focus` 观察问题，例如“确认结尾字幕”，不增加任意时间/文件访问给主模型。`focus` 是不可信查询条件，不是事实或更高优先级指令；静态图片路径不需要它时明确拒绝，避免静默忽略。

Vision 仅获得当前媒体的 storyboard / 帧、runtime manifest、已有中立观察和可选 focus，不获得聊天历史、发送者身份、记忆或主模型工具。仅暴露两个局部工具（名称为建议契约）：

| 工具 | 输入与行为 |
| --- | --- |
| `request_animation_frames` | `{ times_seconds: number[] }`，非空、有界数组；逐项校验实际时轴和总预算，返回按时间定位的画面与映射。 |
| `report_animation_analysis` | 一次提交结构化中立观察：内容概述、动作顺序、可见文字、每项观察的证据 frame ID、未确定项。 |

一次模型回复只接受一个协议动作。未知工具、混合提交/补帧、非法时间和额外字段不得执行；错误可作为有界工具结果供下一轮纠正，但也消耗轮数。普通文字不是最终成功报告。达到预算时可以要求提交已有观察，但仅当总 deadline/轮数仍有余量，不能为了收尾无界追加调用。

最终返回与缓存建议包含：

| 字段组 | 来源与校验 |
| --- | --- |
| `summary`、时序事件、`visible_text` | 模型提供；每个具体断言引用实际提供过的 `frame_id`，文字与事件保留时间位置，不缓存“发送者在讽刺谁”等语境解释。 |
| `uncertainties` | 记录看不清、缺少动作中段等限制；不要求伪精确的概率分数。 |
| 媒体/策略元数据 | runtime 生成格式、尺寸、时长、循环、时间策略和分析版本。 |
| `observed_frames` / `observed_intervals` | runtime 记录本次与有效旧缓存实际看过的状态区间、呈现方式/分辨率和证据来源；不允许模型虚构已看范围。 |
| `coverage` / `stop_reason` | runtime 区分 sampled / all-states-observed / partial 及正常收尾、预算限制等；“全部状态看过”也不保证语义理解完整。 |

输入和输出均用 TypeBox 校验，并限制数组长度、文本长度、JSON 总大小、时间顺序和证据引用。所有观察继续作为不可信媒体数据交给主模型；画面/字幕中的指令不能获得任何执行权限。

## 7. 缓存、增量补看与并发

### 7.1 键与存储

复用 `media_analyses` 的 `(file_unique_id, analysis_version)` 唯一键，新增 `kind = animation`，`description` 保存紧凑概述，`metadata_json` 保存上述经校验的结构。不新增逐帧永久存储表，也不按聊天或提问内容制造一份完整缓存。

动画 `analysis_version` 须有独立 namespace，并包含模型/Provider 身份、prompt、输出 schema、时间归一化、解码/采样、storyboard 策略版本；会改变产物的预算 profile 也需进入指纹。热切换不能把旧模型分析当作新模型缓存。具体编码格式在实施时集中维护，不拼入凭据。

当前[静态图片实现](../../src/capabilities/media/media.ts#L34)是固定 30 天缓存，Sticker 无过期；**不是已经存在的动图策略**。建议动图 TTL 与必填 `retention.online_days` 对齐并可因版本改变失效，具体规则待定；不得无限期留下用户动画观察。保留清理同步覆盖 animation，缓存过期和引用过期是两个独立条件。

### 7.2 读取与补看

- 先 `resolveMedia`、校验当前 Context/TTL/媒体存在，再查缓存或加入 in-flight；从缓存命中到返回、再次补帧的路径都不能绕过授权。失效引用不能靠 `file_unique_id`、旧结果或另一会话补活。
- 无 focus 且缓存有效时直接返回中立观察及覆盖限制，包括明确标记的 partial，不自动重复昂贵分析。
- 有 focus 时，把有效缓存作为初始证据交给有界 vision 循环，由它选择沿用已有观察或请求时间帧；不由字符串匹配猜测缓存是否“语义完整”。首次补帧才需要重新下载/解码源媒体，使用同一策略验证并映射旧帧标识。
- 旧观察不足以确定细节时必须补看；“没有观察到”不能推出“不存在”。focus 原文、聊天内容与语境性答案不写入通用缓存；只合并有图像证据的中立新增观察，不把模型重复叙述当新证据。
- 新分析/升级在内存中形成候选结果，最终验证通过后原子替换。首次失败写 error；升级失败保留旧成功结果，不先把旧行改成 pending 再覆盖成 error。现有[分析 upsert 路径](../../src/capabilities/media/media.ts#L373)会这样覆盖状态，动画升级不能直接复用；升级过程单独通过模型/工具审计记录，无需另建候选结果表。失败也不能返回为完整成功。
- `state = success` 表示协议完成、结果可用，不表示已看全。受预算限制但提交了有效部分观察可保存为 success + partial；未提交有效报告、超时或解码失败不能保存为成功观察。

### 7.3 单次复用与并发

一次分析内保留源文件、有界帧文件和索引，结束后清理临时目录。持久媒体/拼版缓存暂不做；需要跨调用补看时允许重新下载，从测量确认收益后再考虑独立生命周期。

复用现有同键 in-flight 思路：相同媒体/版本的分析串行合并，避免缓存写入丢失。无 focus 的相同请求可以共享；不同 focus 不能直接收到首个问题的结果，先等待并重读新缓存，再决定本次补看。每个调用保留自己的授权、deadline 与工具审计。

首期可保持“实际发起分析者负责本次预算和模型审计”的规则；等待者不重复记模型 Token。共享作业与各调用的等待必须分离：等待者用自己的 deadline/AbortSignal 截止等待并完成自身工具审计，不能直接返回现有共享 Promise 而忽略自己的超时，也不能因此取消共享作业。等待者退出不延长作业；发起者取消则共享作业失败，其他调用得到明确可重试结果，不创建脱离 Invocation 的后台分析。

## 8. 资源、安全与审计边界

| 预算/边界 | 要求 |
| --- | --- |
| 每张 storyboard | 最多 12 个关键帧；含首尾。 |
| 下载 | 不放宽现有 20 MiB 下载上限；实际流量计数，不仅检查声明大小。 |
| 解码 | 单帧像素、累计解码帧/像素、时间轴长度、pass 总工作量、临时磁盘与子进程墙钟均有硬上限，定值前不得上线。 |
| 模型输入 | 总新观察状态数、补帧调用数、累计呈现图片/像素/字节和 Token 分别计数；重复请求不再解码也消耗调用/输入预算。 |
| 轮数与超时 | 整个 read_image 共用绝对 deadline，包含下载、排队、解码、模型重试和补帧；受父 Invocation 取消约束，不逐轮续期。 |
| 输出 | 拼版与独立图的尺寸/字节、结果 JSON 大小均有界；现有静态图的 40M 解码像素和 10 MiB 输出不能被当成多帧总预算。 |
| 并发与费用 | 沿用 Vision semaphore、modelGate 和 chat 日预算；动画循环新增逐轮预算检查与本次累计用量上限，每次请求前检查剩余预算，每次结果计费。当前单次分析入口检查不构成多轮保障，不能只记最后一轮。 |

解码复用[既有 subprocess 边界](../../src/capabilities/media/media-image.ts#L51)：固定可执行文件和 argv、仅受控本地临时文件、最小环境、禁止 shell、禁止网络/播放列表/外部文件引用。GIF/MP4 需显式限定允许的 demuxer/协议并验证单文件结构；`file` 协议白名单本身不等于只允许当前路径。取消/超时要回收进程和文件，不能仅返回错误而遗留 FFmpeg。

局部补帧/报告工具没有 `send`、`execute`、MCP、任意文件访问或发布能力。它们不加入主模型的 capability 注册表。工具文档只说明能力，不扩大授权。

审计沿用现有表和状态，不新建平行日志系统：

- 外层 `read_image` 与局部工具动作都经现有工具审计路径记录参数、成功/拒绝/错误，使用可关联且唯一的调用 ID；记录请求时间、实际状态、重复命中、轮数和预算终止原因。
- 每轮模型调用单独写 `model_calls`，沿用 `vision_chat` 和 `media_analysis_id`；记录本轮实际提供的 `tools_json`，不要误记主模型全部工具，也不要只记首轮。
- 请求/响应记录复用[主模型已有的传输审计方式](../../src/orchestration/agent-runtime.ts#L551)与[图片脱载工具](../../src/platform/model-request-audit.ts#L12)；不得把 storyboard base64、Telegram 下载凭据、未脱敏 Provider 错误写入审计。
- 模型传输成功与结构化报告有效是两件事；报告解析/证据校验失败必须反映在工具/分析错误状态，不因模型返回普通文字就记业务成功。
- 缓存命中无新模型账单；累计失败也保留已发生的用量。格式错误、越界、未授权、解码超限、超时、模型失败和协议错误应有可区分的错误码。

## 9. 实施顺序与验收

以下拆分用于后续开工，顺序以依赖为准：

1. **固化契约与 fixture**：先定下节数值/策略，加入本地可重复的 GIF/MP4 小样本，手工标注显示区间、完整合成画面、短字幕和末尾反转。研究下载脚本不是运行时依赖，不提交整套外部素材。
2. **入库与 Context**：扩展规范化 kind、Schema/新迁移；animation/document 去重；快照保留类别；建立 img_ 但从 figure/directImages 排除，加载器再拒绝误入的动图。
3. **有界时轴/采样/拼版**：建议在现有媒体目录增加一个动画专用模块，复用下载、subprocess 和 Sharp，不先造通用视频框架。先测确定性取帧，再接模型。
4. **Vision 循环与缓存**：保留静态图/Sticker 路径，加入两个私有工具与 TypeBox 结果校验；复用配置快照、并发门、审计和预算；加入增量合并、失败保旧缓存及保留清理。
5. **文档与回归**：更新 [image-inspection Skill](../../src/system-resources/skills/image-inspection/SKILL.md)、[媒体流程](../telegram-agent-flow.md)、[数据层](../data-layer.md)、[验证](../verification.md)，以及公开用户指南。若新增配置字段，同步 schema、示例、参考与热更新边界；本方案不要求新增 Admin 写端点。

## 10. 开工前需要定值的参数

- **预算**：首轮以外的总状态/呈现图片数、单次补帧数组长度、总轮数、总 deadline、重试与 Token 上限；24 不自动生效。
- **时间策略**：GIF 缺失/零/1 cs delay 的规范口径及其版本；首期是否采用研究公式，MP4 末帧结束时间的可接受来源。
- **图像/解码资源**：拼版布局与单格分辨率、整图尺寸/输出字节、源时长、每帧与累计像素、帧数、磁盘、pass 和子进程并发上限。
- **缓存**：与 online retention 的 TTL 对齐方式、版本指纹字段；是否启用本文建议的可选 focus 跨调用补看，必须在接口与测试中明确，而不是只实现首轮却宣称可持续补看。

这些参数应由受控 fixture 和小型人工标注评测定案；不要把便利样本最大值或“12 格”反推为服务器安全上限。可以先开展 fixture/纯解码实验，未决项没有定案前不应默认放大生产预算。
