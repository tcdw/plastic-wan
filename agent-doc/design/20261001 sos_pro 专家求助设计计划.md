# sos_pro：便宜模型向强模型求助

状态：Phase 1 范围与设计决定已确认，实施未开始。本计划不依赖「MCP Server 热更新」：专家只用 `web_fetch`，专家插件不引用、不持有 `McpManager`；两个计划在 `src/application.ts` 之外没有交集，实施先后不限。专家若日后要使用 MCP 工具，那一项应排在 MCP 热更新之后。

调研基线：`7d7b31976d76bd2ee5073f3205a67364a624ee70`（2026-10-01）。本文的源码引用均在该基线上核对过；行号会漂移，实施前按符号名重新核对。下文区分「用户决定」「本文建议」与「尚未定值」。

## 1. 目标与范围

给主 Agent 模型（便宜模型）一个 `sos_pro` 工具：遇到复杂问题时把问题交给另一个更强、更贵的模型（下称「专家」），专家的结论稍后回到便宜模型手里，由它用塑料碗的人设转述给群友。

约束来自项目定位：BYOK、模型费用由部署者承担、默认用廉价模型。专家只在少数问题上出场，且花费必须有硬上限。

Phase 1 不包含「仅在用户明确要求时才放行」这一态，见第 10 节。

## 2. 决定一览

| 层级 | 内容 |
| --- | --- |
| 用户决定 | `sos_pro` 作为**直接暴露**的工具注册（同 `zzz`），不走 `execute` + Skill；程序内部以**插件**形态实现。 |
| 用户决定 | 插件可以**声明其它插件为依赖**；专家插件依赖 `web-fetch`。 |
| 用户决定 | 求助是一个**长程任务**：工具立即返回，专家在后台运行，结论以完成回执在独立轮次回到便宜模型。不新建 `invocations` 行。 |
| 用户决定 | 等待提示由塑料碗**自己发一条消息**表示去问专家了，文案由部署者通过 Prompt 调整。不由 runtime 代发，不用 typing 状态。 |
| 用户决定 | 专家子运行**只暴露 `web_fetch`**。 |
| 用户决定 | 专家的输入：便宜模型手写的 `relevant_context`，加 runtime 附带的**最近 5 条**消息原文（5 为暂定值）。 |
| 用户决定 | 提问者由工具参数 **`for_message_id`** 指明。 |
| 用户决定 | 每群开关 `chats[].sos_pro`，Phase 1 只有**关闭 / 自动**两态，默认关闭。 |
| 用户决定 | 每日**金额预算只管专家**；便宜模型仍只受全局 Token 预算约束。单一阈值，**没有 80% 降级档**。 |
| 用户决定 | **专家不睡觉**：金额预算触顶只让 `sos_pro` 不可用，不写 `bot_sleep_until`，不暴露 `zzz`。 |
| 用户决定 | 专家的 Token **计入全局 Token 熔断**。 |
| 用户决定 | 专家回执**绕过每日预算**直接送达（`bypassDailyBudget: true`）：已花钱的答案必须送到，接受这部分有界超支。 |
| 用户决定 | 回执**自动 @ 提问者**，但仅当该提问者明确 @ 了塑料碗或回复了塑料碗的消息。 |
| 用户决定 | 需要为专家子运行留审计入口。 |
| 本文建议 | Token 熔断只在**创建任务时**检查；已在运行的专家跑完（受自身上限约束），避免钱花一半答案作废。 |
| 本文建议 | **专家回执轮内禁止再调 `sos_pro`**，由代码判断，防止回执触发新求助的循环。 |
| 本文建议 | 同一 Conversation 同时只允许一个进行中的专家任务。 |
| 本文建议 | 附带的 5 条消息以 `for_message_id` 那条为终点、跨批次选取、逐条截断。 |
| 本文建议 | 私聊不加自动 @。 |
| 尚未定值 | 见第 11 节。 |

## 3. 已核对的起点

- **Invocation 不适合承载专家运行。** `invocations.bucket_id` 非空，且有 `one_running_invocation_per_conversation` 唯一索引（`src/store/schema.ts`）；`AgentRuntime.#runInvocation`（`src/orchestration/agent-runtime.ts`）整个闭包与 Conversation Context、注入、send 屏障、GC 耦合，无法抽出一半复用。
- **Tool 内调用另一个模型已有先例。** `MediaService.createReadImageTool`（`src/capabilities/media/media.ts`）使用独立模型、独立超时，`model_calls` 以 `vision_chat` 角色挂在父 Invocation 上，用量记入该群的 `daily_usage`。
- **按条件直接暴露工具已有先例。** `refreshZzz` 在 turn 边界增删 `zzz`；工厂函数拿得到 `InvocationContext.chatId`，可以按群决定是否注册。
- **长程任务服务已存在，但没有执行器。** `LongTaskService`（`src/store/long-tasks.ts`）持久化任务与完成回执，无 timer 的任务等待插件调用 `complete` / `fail`；它没有 worker、running 状态、retry 或插件生命周期钩子。无 timer 的 `waiting` 任务按设计永久保留，不会因创建者结束而被清理。
- **回执投递已具备所需策略。** `DeliveryPolicy` 支持 `bypassDailyBudget` 与 `mentionUser`，在任务创建时冻结；mention 由 `send` 在回执轮第一次成功的文本发送时附加（`completionMention`，`src/capabilities/send-tool.ts`）。回执以 `<untrusted_task_receipt>` 注入，且不继承上一位发言者的 caller 权限。
- **单价与单次金额已存在。** 每个模型的 `cost`（输入、输出、缓存读、缓存写，每百万 Token）是配置必填项，可为 0；Pi 的 `calculateCost` 据此得到 `usage.cost.total`，已写入 `model_calls.cost`。缺的是按日汇总与预算闸门。
- **Token 预算是全局的。** `readDailyTokenBudget`（`src/store/sleep.ts`）对当天所有 Chat 求和；用量按 Chat 写入 `daily_usage`，主键为 `(utc_date, scope, resource, metric)`。
- **插件接口目前只有两种贡献。** `AgentPlugin`（`src/plugins/plugin.ts`）只能声明 `skills` 与经 `execute` 调用的 `capabilities`；`InvocationScope` 只含 `config`、`context`、`deadline`、`audit`、`tasks`，拿不到 Store、模型注册表或 Invocation 快照。组合根传给插件的是 `configStore.current().config`，不是本次 Invocation 的快照。
- **「谁明确找过塑料碗」没有按消息保存。** `matchTriggerKind`（`src/platform/participation.ts`）能区分 `mention` 与 `reply_to_bot`，但只在配置了 `participation` 的群、活跃时段之外运行，结果只写入 `conversation_attention`（每个 Conversation 一行，只留最近一次）。送进模型的消息快照不含 entities。
- **稳定 system prompt 的任何变化都会清空 Conversation Context。** `ConversationContextStore.open()` 在哈希不一致时删除该 Conversation 的全部历史与引用；Skill 索引是哈希的一部分，且全局渲染、不按群区分。

## 4. 为什么这样选

- **直接暴露而不是 Skill。** 新增 Skill 文档会改变 Skill 索引，部署后所有 Conversation Context 重建一次；若再按群过滤索引，切换某群开关会清空该群历史。直接暴露的工具不进 system prompt 哈希，开关变化只让 provider 前缀缓存失效一次。
- **长程任务而不是阻塞式工具调用。** 阻塞会让主循环卡在 Tool 里：占一个 `agent.max_concurrency` 槽位、挡住同群其它 Topic，等待时间超过 provider 缓存 TTL 时便宜模型的前缀缓存也会过期。改为长程任务后这些都不存在；「我去问专家了」成为该轮的正式回复，答案在独立回执轮发送，不会出现占位消息让 send nudge 失效、占用 send 屏障的问题。
- **金额预算只管专家。** 这样不必在主循环的各个 Token 闸门旁平行加一套金额闸门，预算检查全部落在专家插件自身范围内；只有专家模型参与计价，也就不存在跨币种相加，预算单位即该模型 `cost` 的单位。代价是便宜模型的账单没有金额上限，只有 Token 熔断。
- **依赖拿「工厂」而不是「造好的工具」。** 专家是后台任务，活得比创建它的 Invocation 久；父 Invocation 的 `web_fetch` 实例绑定的是父 Invocation 的 deadline。依赖方应取得被依赖插件的定义，用自己派生的 scope 再调用其 `capabilities()`。

## 5. 工具契约与运行流程

### 5.1 `sos_pro` 输入

| 字段 | 说明 |
| --- | --- |
| `question` | 交给专家的问题。 |
| `relevant_context` | 便宜模型手写的背景。工具描述须明确：专家看不到群聊，需要的背景必须写进来。 |
| `constraints` | 可选，回答的限制或要求。 |
| `for_message_id` | 这次求助是替哪条消息问的，取自当前可见消息。 |

各字段长度上限须在代码里再校验一次：声明了 `tool_schema_keywords: 'minimal'` 的模型会被剥掉 `maxLength` 等关键字。

### 5.2 流程

```text
便宜模型调用 sos_pro
  → 校验：群开关、回执轮禁用、金额预算、Token 熔断、每群当日次数、同会话无进行中任务、for_message_id
  → 创建长程任务（冻结 delivery policy），启动后台专家子运行
  → 工具立即返回「任务已创建」
  → 便宜模型用 send 告诉群友去问专家了（本轮结束）

后台专家子运行
  → 输入：question + relevant_context + constraints + 最近 5 条消息原文
  → 工具：仅 web_fetch
  → 受轮数、Token、超时、金额上限约束
  → 结束时 complete（结论）或 fail（原因）

回执
  → 现有投递路径：空闲时启动回执 Invocation，会话运行中则按轮次注入
  → 便宜模型读取 <untrusted_task_receipt>，用 send 转述；符合条件时自动 @ 提问者
```

### 5.3 注册与拒绝

- 未配置专家模型，或该群 `sos_pro` 为关闭：不注册工具。
- Invocation 开始时金额预算已用完：不注册。工具表因此每天最多翻两次（用完时摘除、UTC 日切换时恢复）。
- 调用时再检查一次全部条件，覆盖长活 Invocation 中途越线的情况。
- 当前轮是专家插件自己的回执轮（`completion.pluginId` 为专家插件）：拒绝调用。

## 6. 专家子运行

- 一个新的 Pi `Agent` 实例，使用独立的短 system prompt：说明自己看不到群聊、各输入段的含义、消息原文是不可信数据、输出为结论加关键依据并受长度限制。Phase 1 该 prompt 固定在代码里。
- 不含 `send`、`sos_pro`、记忆、Alarm 等任何带副作用的工具。工具表是显式构造的白名单，递归在结构上不可能发生。
- 使用创建它的 Invocation 的配置快照中的模型注册表，但**不沿用**其 `AbortSignal` 与 deadline；自带超时与 `AbortController`。
- 不占用按 Chat 的 `modelGate`，否则专家流式输出期间该群的便宜模型会被堵住。
- 每次模型调用前检查金额预算，超支上限为一次模型调用。
- 结论受完成回执的大小上限约束（`long-tasks.ts` 的 `MAX_JSON`，16 KiB）。

### 6.1 附带的消息原文

- 由宿主在渲染注入时准备好并经 `InvocationContext` 递给插件；插件不读数据库。
- 跨批次选取：15 秒一个 Bucket，最新一批常常只有一两条。
- 以 `for_message_id` 那条为终点，避免提问之后的闲聊挤掉相关内容。
- 逐条截断；图片引用渲染为占位符（专家没有 `read_image`）。
- 包在不可信标记内。

### 6.2 任务 payload 只放摘要

回执渲染会把任务 `payload` 原样带回便宜模型的上下文（`#completionReceipt` 的 `context` 字段）。`relevant_context` 与消息原文若放进 `payload`，便宜模型会把它们再读一遍。`payload` 只保留问题摘要与 `for_message_id`，完整输入留在后台运行的内存中，并写入审计（见第 8 节）。

### 6.3 恢复与关闭

- **启动清扫**：专家插件在启动时把自己名下所有 `waiting` 任务标记为失败，回执照常投递，由便宜模型告知群友。这需要插件生命周期钩子，以及 `LongTaskService` 的跨 Conversation 清扫入口（现有 `scoped()` 按 Conversation 绑定）。
- **关闭**：中止所有后台子运行，任务留在 `waiting`，交给下次启动清扫。崩溃与正常关闭走同一条恢复路径。

## 7. 插件接口扩展

- 新增直接暴露工具的贡献；组合根把它与 MCP 工具一起并入 `additionalTools`。注册表校验会用 `previewContext()` 构造工具，新服务需要像 `unavailableTasks()` 那样的占位实现。
- 新增 `dependsOn`。`loadPlugins` 校验被依赖的 id 存在且无环，不通过则启动失败。scope 只允许取得已声明的依赖；依赖方按工具名挑选所需能力。启动钩子按依赖顺序执行。
- 新增启动钩子。
- `InvocationScope` 需要补充：
  - **模型调用服务**：由宿主绑定好预算检查、`model_calls` 审计与记账后递给插件，插件不直接持有 Store 或 Runtime。它同时是前置重构的落点：`agent-runtime.ts` 与 `media.ts` 现在各有一份几乎相同的记账代码。
  - **Invocation 快照**：模型注册表必须来自快照，而不是 `configStore.current()`。
  - **本群的解析后配置**与**最近消息原文、消息的直接称呼标记**。

不做版本约束、可选依赖或运行时启停：`BUILTIN_PLUGINS` 是固定列表，目前只有一条依赖边。

## 8. 预算、记账与审计

### 8.1 金额预算

- 只统计专家的模型调用。每次调用结束时把 `usage.cost.total` 换算为整数微单位，累加到 `daily_usage`（按 Chat 存，全局求和，与 `model_tokens` 同一模式；`amount` 是 bigint，不能直接存小数）。
- 全局单一阈值，按 UTC 日重置。
- 检查点：Invocation 开始时（决定是否注册）、工具调用时、子运行每次模型调用前。
- 精度限制：端点不上报 usage 或缓存 Token 时记为 0；Pi 支持的阶梯价未在配置中暴露；流直接失败的调用没有 usage。

### 8.2 其它限额

- 每群每日调用次数：`daily_usage` 中按 Chat 的独立计数，不共享全局额度。
- 专家的 Token 计入该群的 `model_tokens`，从而计入全局 Token 熔断。

### 8.3 审计

- `model_calls.role` 的 CHECK 约束需要一次迁移以加入专家角色（重建表，先例为 `009_harness_nudge.sql`）。
- 子运行的 `model_calls` 与 `tool_calls` 会在父 Invocation 结束之后才产生。给两张表增加任务 ID 列，使审计按任务聚合，而不是让已完成的 Invocation 花费继续增长。
- 专家实际收到的输入（含 runtime 附带的消息原文，它们不在工具参数里）与最终输出按任务 ID 保存一份；否则只有开启 `developer.record_model_payloads` 才看得到。
- `tool_calls.tool_call_id` 全局唯一。子运行的工具调用 ID 加前缀，避免与主 Agent 的 ID 冲突。

## 9. 自动 @ 提问者

- 在入库时复用 `matchTriggerKind`（关键词传空表）判定消息是否明确 @ 了塑料碗或回复了塑料碗的消息，结果按消息修订保存。放在修订级别是因为编辑可能加上或去掉 @。不在渲染时从快照文本反推：那是第二套判定逻辑，且没有 entities。
- `for_message_id` 需同时满足：属于当前批次的新消息、带有直接称呼标记、发送者可见。全部满足时把该发送者冻结为 `delivery.mentionUser`；否则任务照常创建，不加 @。
- 私聊不加 @。

## 10. 明确不做与留待以后

- **「仅在用户明确要求时」这一态**：Phase 1 不做。之后可能用 jev 这类决策模型判定。注意 2026-09-22 的 hold gate 离线评估中 jev 的 AUC 仅 0.52–0.56、每次增加约 1.9 秒，相关代码已删除；重新引入前需要针对新问题做离线评估。
- 80% 降级档、便宜模型的金额预算、多币种。
- 专家使用 MCP 工具、`read_image` 或接收图片。
- 专家任务的取消入口、进度状态与自动重试。
- 插件的版本约束、可选依赖、按配置启停。

## 11. 开工前需要定值的参数

- 专家子运行的最大轮数、单次运行 Token 上限、超时。
- 每日金额上限的配置位置与默认值；每群每日次数上限。
- 结论长度上限；附带消息的条数（暂定 5）与逐条截断长度。
- 专家模型配置块的位置与字段名（先例：`web_fetch` 是顶层可选块），以及它与 `chats[].sos_pro` 是否列入热更新白名单（`src/platform/config-diff.ts`；未列入的字段只能重启生效）。
- 直接称呼标记的列名与存放的表。
- 审计中专家输入与输出的存放位置。

## 12. 风险

- **提示注入与外泄**：专家读到的网页可以诱导它用 `web_fetch` 把输入里的群聊内容拼进 URL 发出。这条通道便宜模型今天就有，但专家的上下文里现在直接带着消息原文。结论回到便宜模型后，后者持有 `send`、记忆与 Alarm；回执已带不可信标记。
- **成本**：便宜模型必须用输出 Token 写出 `relevant_context`；每次求助多一轮便宜模型（回执轮），会话空闲超过缓存 TTL 时这一轮是冷读。进程在专家运行中途崩溃时，已花的钱不会换来答案。
- **体验**：群友得到「去问专家了」之后，答案的到达时间不确定；进程重启会把它变成一条失败回执。
- **转述失真**：`send_max_text_length` 与人设会压缩专家的结论。附带原文只解决输入侧的失真，不解决输出侧。
- **与既有计划的文件交集**：见第 14 节。

## 13. 实施顺序

每一步可独立验证；Provider 相关测试使用现有 Faux。

1. **前置重构**：把模型调用的审计与记账抽成共用服务，`agent-runtime.ts` 与 `media.ts` 改用它。验收：现有测试不变，审计行与 `daily_usage` 不变。
2. **插件接口**：直接暴露工具的贡献、`dependsOn` 与环检测、启动钩子、scope 补充项。验收：缺失依赖与环状依赖在启动时失败；现有插件行为不变。
3. **直接称呼标记**：入库时判定并保存，经注入递给 `InvocationContext`。验收：@、回复、编辑后增删 @ 的修订各有断言。
4. **配置与迁移**：专家模型配置块、`chats[].sos_pro`、语义校验、doctor 探针、`model_calls.role` 与任务 ID 列。
5. **专家子运行与金额预算**：先不暴露给模型。验收：轮数、Token、超时、中止、金额触顶、审计归属、工具白名单。
6. **工具暴露与长程任务接线**：两态开关、每群次数上限、回执轮禁用、启动清扫、自动 @。验收：断言 `tool_registry_json`、回执投递策略、重启后任务以失败回执结束、canonical history 的落盘状态。
7. **Admin Panel、`/status`、用户文档与 `agent-doc` 主题文档同步。**

## 14. 与既有计划的关系

2026-10-01 对照了两份历史设计。结论：没有方向性冲突；有两处对旧计划的偏离需要明示，另有一组约束用来保证本计划不给 Core 分离 Epic 增加迁移项。

### 14.1 [20260918 内置 Agent 插件化计划](20260918%20内置能力插件化计划与结论.md)

该文的状态已落后于源码：`definePlugin` / `loadPlugins` 已存在，`web-fetch` 与 `alarm` 已是插件，文中「曾讨论的 `host.tasks`」已以 `LongTaskService` 的形式落地；memory 尚未迁入插件。

- **一致**：插件通过窄宿主接口取得能力，不持有 Runtime、全局配置或全局数据库（本文的模型调用服务）；不做 `beforeX` / `afterX` 事件钩子总线；前端固定实现；不新增 Skill，因而不触发该文风险 4 提到的 Context 重建。
- **采用**（本文建议）：该文建议「定义与运行实例分开，`setup(host)` 返回贡献」。专家插件正需要这个形态：它有实例状态（后台运行的 `AbortController` 集合）和启动动作（清扫 `waiting` 任务）。第 7 节的「启动钩子」按 `setup(host)` 落地，不另加一个独立的钩子名。
- **偏离一**：该文要求沿用 `execute`，保留「原语、MCP、内部能力」三类的区别。本文让插件贡献直接暴露的工具，成为第四类，理由见第 4 节。它走已有的直接暴露路径，不是新的工具分发体系，也不可经 `execute` 调用。
- **偏离二**：该文把「依赖解析」列入不做清单，语境是用户插件平台。本文的 `dependsOn` 只做内置插件之间的存在性与环检测。用户已决定。
- **待补语义**（本文建议）：该文第 4 节要求功能关闭后不再提供后台触发，并单独定清停用时待执行任务的处理。`chats[].sos_pro` 关闭或专家配置被移除后，不再接受新求助；已创建的任务跑完并照常投递回执，因为钱已经花了。

### 14.2 [20260928 Core 与 Telegram Adapter 分离 Epic](20260928%20Plaswan%20Core%20与%20Telegram%20Adapter%20分离%20Epic.md)

该 Epic 的目标是让 Harness 不再解释 Telegram，为接入其它 IM 留条件；它不是插件框架。它明确不实施 subagent 与通用后台 executor，理由是「当前没有这些能力需要随拆分迁移」。本计划落地后这个前提不再成立，因此专家相关代码应按平台中性的 Core 侧能力来写：

| Epic 任务 | 交集 | 本计划遵守的约束 |
| --- | --- | --- |
| PW-CORE-01 装配规则一致 | 插件直接工具进入工具装配 | 与 MCP 工具经同一个装配函数进入注册表预览、真实运行、热配置候选校验三条路径 |
| PW-CORE-03 收窄插件 scope | 两边都改 `InvocationScope` | 专家插件只拿自己的配置块与宿主解析好的本群开关，不读完整 `RawConfig` 中的 Telegram 部分；模型注册表取自 Invocation 快照 |
| PW-CORE-02 / 04 消息投影与 metadata | `for_message_id`、直接称呼标记、最近消息原文 | `for_message_id` 视为不透明 message key；直接称呼标记在 Telegram 入库边界计算，以中性布尔值提供；消息原文以渲染好的文本提供 |
| PW-CORE-06 任务 owner / delivery 中性化 | 专家是 `mentionUser` 的第二个生产者 | 插件不自己构造 Telegram 用户身份，沿用宿主给出的发送者对象，与 Alarm 同一模式，届时一起迁移 |
| PW-CORE-07 usage key | 专家的 Token 与金额记账 | 模型调用记录器接受不透明的 usage key，不在内部假定 Chat ID |

后台执行保持插件私有，不把 `LongTaskService` 扩展成通用 executor。

实施先后：本计划与 PW-CORE-01、PW-CORE-03 有真实的文件交集（`src/application.ts`、`src/plugins/plugin.ts`、工具装配）。遵守上表约束时，后做的一方只需小幅适配。若本计划先落地，该 Epic 的「已核对的起点」中插件一行与「不实施 subagent」的说明需要更新。
